## 1. Задание (оригинал, не менять смысл)

Мини-проект «Дневник смен водителя». Стек любой. Можно пользоваться ИИ.
Данные: JSON-файл с поездками. Каждая поездка — время начала, время окончания, сумма, способ оплаты (cash/card), комиссия.
Что должно работать:
1. Сервер отдаёт по API список поездок за выбранный день и сводку за день: число поездок, выручка, комиссия, «на руки», разбивка наличные/карта.

3. Добавление поездки через API с проверкой данных (сумма > 0, окончание позже начала). Повторная отправка той же поездки не должна создавать дубль.
4. Тесты на расчёт сводки и на защиту от дублей.
Сдать: публичный репозиторий с README (как запустить, что сделано), по желанию скриншоты, и коротко — как использовали ИИ, где он ошибся, что исправили.

## 3. Бизнес-правила (зафиксировать в README → «Допущения»)

1. **Деньги** — целые числа в тенге (`int`), никакого float ни на сервере, ни в клиенте.
2. **Часовой пояс.** «День» = дата **начала** поездки в часовом поясе Алматы. Используем **фиксированный оффсет UTC+05:00** (`timezone(timedelta(hours=5))`), а не `ZoneInfo("Asia/Almaty")`. Причина: на Windows нет системной базы tz (нужен пакет tzdata), а в старых версиях tzdata Алматы = UTC+6 (Казахстан перешёл на UTC+5 в 2024). Фиксированный оффсет детерминирован. Объяснить это в README.
3. Поездка через полночь относится ко дню начала.
4. **Время на вход** — ISO 8601 **обязательно с оффсетом** (`+05:00`, `Z` и т.д.). Время без оффсета → 422. Внутри всё приводим к UTC+05:00, в ответах API отдаём ISO с `+05:00`.
5. **Сводка за день:** `date`, `trips_count`, `revenue` (Σ amount), `commission` (Σ commission), `net` = revenue − commission («на руки»), `cash: {amount, count}`, `card: {amount, count}`. Пустой день → все нули (не 404).
6. **Валидация POST** (ошибки → 422 с понятным сообщением на русском или английском, единообразно):
   - `id` — непустая строка после trim, до 64 символов;
   - `amount` — int > 0;
   - `commission` — int, 0 ≤ commission ≤ amount;
   - `payment` ∈ {`cash`, `card`};
   - `end` > `start`;
   - лишние поля запрещены (`extra="forbid"`).
7. **Идемпотентность / дубли:**
   - первое создание → **201** и поездка;
   - повторный POST с тем же `id` и теми же данными → **200** и существующая поездка, дубль не создаётся;
   - тот же `id`, другие данные → **409 Conflict** с понятным сообщением;
   - «те же данные» сравниваем **после нормализации**: `2026-10-01T08:10:00+05:00` и `2026-10-01T03:10:00Z` — один и тот же момент, это НЕ конфликт;
   - уникальность обеспечивает **БД** (`id TEXT PRIMARY KEY`). Алгоритм без гонки: пытаемся `INSERT` → при `IntegrityError` читаем существующую запись → сравниваем → 200 или 409. Не делать «сначала SELECT, потом INSERT» как единственную защиту.
8. **Seed:** при старте сервер загружает `/data/trips.json` в БД через `INSERT OR IGNORE`. Повторный запуск не создаёт дублей. Если в seed тот же id с другими данными, чем в БД — пишем warning в лог, не падаем. Каждая запись seed проходит ту же валидацию; невалидная запись — warning и пропуск.
9. В таблице храним колонку `day` (YYYY-MM-DD по Алматы) с индексом — по ней фильтрация. Сортировка списка — по `start`.

## 4. Данные: /data/trips.json

Сгенерируй реалистичный файл:
- 4 дня подряд (2026-10-01 … 2026-10-04), 6–12 поездок в день;
- обе формы оплаты, суммы 800–6000 ₸, комиссия ≈ 15% (целое число);
- **одна поездка через полночь**, например старт 2026-10-02 23:40, конец 2026-10-03 00:15 → относится к 02.10;
- хотя бы одна поездка с временем, записанным с другим оффсетом (например в `Z`), которая по Алматы попадает в определённый день — для проверки нормализации;
- id вида `t1`, `t2`, … уникальные.

## 5. API

| Метод | Путь | Ответ |
|---|---|---|
| GET | `/api/days` | отсортированный список дат `["2026-10-01", ...]`, за которые есть поездки |
| GET | `/api/trips?date=YYYY-MM-DD` | список поездок за день, по `start`; неверная дата → 422 |
| GET | `/api/summary?date=YYYY-MM-DD` | сводка за день |
| POST | `/api/trips` | 201 / 200 / 409 / 422 по правилам выше |
| GET | `/health` | `{"status": "ok"}` |

- Swagger на `/docs`, в схемах есть примеры (`json_schema_extra`).
- CORS включён (для разработки `allow_origins=["*"]`, в README отметить, что в проде ограничить).
- Путь к БД и к seed — через переменные окружения с дефолтами; в тестах — временная БД.

## 6. Тесты (pytest)

**Чистая функция сводки** (`summary.py`, без API и БД — на списке объектов):
- обычный день: правильные revenue, commission, net, cash/card amount и count;
- пустой день → нули;
- только cash; только card;
- функция определения дня: поездка через полночь → день начала; время в `Z` корректно переводится в день по Алматы (например `2026-10-01T19:30:00Z` → `2026-10-02`).

**API:**
- GET `/api/summary` и `/api/trips` за день из seed — числа совпадают с ручным подсчётом; сортировка по start;
- поездка через полночь видна в дне начала и не видна в следующем;
- валидация → 422: amount ≤ 0, end ≤ start (и равно, и раньше), commission > amount, commission < 0, неверный payment, пустой id, время без оффсета;
- дубли: первый POST → 201; тот же объект ещё раз → 200, кол-во поездок за день не изменилось; тот же id, другая сумма → 409; тот же момент в другом оффсете → 200 (не 409);
- повторная загрузка seed (вызвать дважды) не меняет количество записей.

Логику сводки держи отдельно от API — тесты сводки не должны поднимать сервер.

## 7. Клиент (Flutter)

**Конфиг:** адрес API через `--dart-define=API_BASE_URL=...`, дефолт `http://localhost:8000`. В README: для Android-эмулятора `http://10.0.2.2:8000`.

**Дизайн — «дашборд водителя такси»:** Material 3, `colorSchemeSeed` тёплый янтарный/жёлтый, светлая и тёмная тема по системе. Крупные цифры, минимум элементов, читается с одного взгляда. Адаптивно: на широком экране контент по центру с max-width ~600.

**Экран дня (один экран):**
1. **Сверху — переключатель дня:** `‹  Чт, 1 октября  ›`. Стрелки переходят на предыдущий/следующий день **из `/api/days`** (на краях стрелка неактивна). Тап по дате → список/календарь доступных дней. Даты на русском (`intl`, локаль `ru`). При запуске открывается последний доступный день.
2. **Карточка сводки:** самая крупная цифра экрана — **«На руки»**. Под ней мелко: выручка, комиссия, поездок. Ниже два блока/чипа: 💵 Наличные (сумма · кол-во) и 💳 Карта (сумма · кол-во).
3. **Список поездок:** в строке `08:10–08:32 · 22 мин`, справа сумма жирным, иконка оплаты (`Icons.payments` / `Icons.credit_card`), комиссия серым мелко. Поездку через полночь пометить (например «→ 00:15 след. дня»).
4. **Состояния:** загрузка (индикатор), пустой день («Поездок нет»), ошибка сети (текст + кнопка «Повторить»). Pull-to-refresh.
5. **Формат денег:** `2 400 ₸` (пробел между разрядами, знак после числа). Отдельная функция форматирования.

**Добавление поездки:** FAB «+» → bottom sheet с формой:
- поля: дата и время начала, дата и время окончания (по умолчанию дата = выбранный день), сумма, комиссия (по умолчанию подставляется 15% от суммы, можно изменить), способ оплаты (SegmentedButton cash/card);
- валидация на клиенте — те же правила, ошибки под полями;
- **id генерируется (uuid) один раз при открытии формы** и переиспользуется при повторной отправке — так повтор после сбоя сети не создаёт дубль; кнопка «Сохранить» блокируется на время запроса;
- ответы: 201 → закрыть форму, обновить день, snackbar «Поездка добавлена»; 200 → snackbar «Такая поездка уже есть»; 409 / 422 → показать текст ошибки сервера в форме;
- после добавления переключиться на день новой поездки (и обновить `/api/days`, если день новый).

**Код клиента:** `lib/api/` (клиент API + модели), `lib/screens/`, `lib/widgets/`, `lib/utils/format.dart`. `flutter analyze` без ошибок. Минимум 1–2 теста: форматирование денег и длительности.

**Облачное окружение:** попробуй поставить Flutter SDK в облачной машине, чтобы прогнать `flutter analyze` и `flutter test`. Если не получится (сеть/размер) — сообщи мне, запиши в AI_NOTES, и эти команды я запущу локально.
